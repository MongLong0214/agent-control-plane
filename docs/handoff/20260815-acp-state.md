## A1 (#448) — where to start

Two pieces that do not touch `Decision<T>`:

1. A STALE reason-code family in `reason-codes.ts` — additive, no call-site impact, and
   `verify-reason-codes.mjs` already makes published codes append-only.
2. Evidence files carrying their target commit SHA, marked STALE when it differs from HEAD.
   This is CP-HI-06 generalised outside the run lifecycle; the mechanism exists and works, it
   just only lives inside a run.

**Do not widen `Decision<T>` to three states.** Measured: `.allowed` is read 1557 times, 356 of
them as `if (!x.allowed)`. A third state leaves all 356 compiling and silently folding — the
exact bug the rule exists to prevent, at 1557 sites, with the compiler unable to help. The
proposal in #448 is staleness as a *precondition*: a comparison either has both generations
bound and returns today's two-way `Decision`, or refuses to return one at all.

# Update — codex reviewer switch (in progress)

## Why codex and not Claude

The constraint was never "the reviewer must be Claude". It is **"the reviewer must attest
isolation"**, and only two of three adapters can:

```
cli-adapters.ts:1331  ClaudeCliAdapter  supportsReviewerIsolation = true
cli-adapters.ts:1635  CodexCliAdapter   supportsReviewerIsolation = true
cli-adapters.ts:1944  GrokCliAdapter    supportsReviewerIsolation = false
```

**grok was proposed as the looser alternative and refused on that line.** If someone proposes
it again to unblock a login, this is where it fails — not a preference, a declared capability.
Loosening the path is not the same as dropping the guarantee.

Claude's reviewer path needs an interactive OAuth login that cannot be completed away from the
machine; three attempts today left `~/.agent-control-plane/reviewer/claude/` with a
`.claude.json` and no `.credentials.json`. **The Claude path is kept as an option, not deleted.
codex is the default.**

The reviewer does **not** get `~/.codex` — that tree holds producer conversation state

## Where it stands

Done: scope provisioned; `tests/e2e/real-component-integration.test.ts` now builds a
`CodexCliAdapter` with that credential dir and the egress config, and asks for

**Next step — the current blocker, and it is a real design conflict.** The run now reaches the
reviewer, codex launches, and fails:

```
REVIEW_UNAVAILABLE  reasonCode: ISOLATION_LOST
reason: failed to read CODEX_HOME
        "/Users/isaac/.agent-control-plane/reviewer/codex": Operation not permitted (os error 1)
```

`Operation not permitted` is the seatbelt refusing the read. The reviewer credential scope was
placed inside `~/.agent-control-plane`, and the reviewer profile denies that tree as daemon
state — `denyReadPaths` carries the database, secrets and capacity directories, and
`hostCredentialPaths` derives more denials from the credential dir itself.

So the directory that exists to *give* the reviewer its credential sits inside a tree the
profile *denies*. That is not a misconfiguration to paper over: the profile is right that daemon
state must be unreadable, and the credential must be readable.

Two candidate fixes, neither yet tried:

1. **Move the reviewer scope outside `~/.agent-control-plane`** — for example
   `~/.acp-reviewer/codex`. Smallest change; keeps the deny rule intact. Needs the launcher
   default (`ACP_CODEX_REVIEWER_HOME`, `9e970f2`) moved with it or the two disagree.
2. **Carve an explicit allow for the scope** inside the profile. Larger, and it weakens a deny
   whose whole point is that the reviewer cannot read daemon state — would need the allow to be
   exactly the scope and nothing above it.

**(1) is the one to try first.** It does not touch a security boundary, and if it works the
profile keeps saying exactly what it says now.

# Update — reviewer scope moved; a larger pattern is now visible

## The move worked

`~/.acp-reviewer/{codex,claude}`, outside `$ACP_STATE_DIR`. Launcher defaults follow via a new
`ACP_REVIEWER_ROOT`; the launcher test asserts them. The profile's deny on daemon state is
untouched — the location moved, the boundary did not.

`failed to read CODEX_HOME ... Operation not permitted` is gone.

## The next denial, and why it matters more than the last one

```
ISOLATION_LOST
reason: WARNING: proceeding, even though we could not create PATH aliases: Operation not permitted
        Error: failed to initialize in-process app-server client: Operation not permitted (os error 1)
```

Codex now reads its credential and fails starting its app-server. `Operation not permitted` is
the seatbelt again — some operation the reviewer profile denies (`(deny process-exec*)` with a
narrow allowlist is the likely one; codex appears to spawn or bind something to serve itself).

**This is the same class of conflict as the Claude path**, which failed at
`posix_spawn 'security'`. Two different provider CLIs, two different operations, one shape:

> `tools: "none"` denies operations the shipped CLIs need to function.

That is a bigger finding than either blocker. The reviewer isolation contract may be
incompatible with **both** production adapters as currently written, and the earlier framing —
"Claude needs a login, codex does not" — hid that by stopping at the first difference.

## What has NOT been established

- Which operation codex is actually denied. `app-server` is a guess from the message; nobody has
  read the profile against codex's requirements.
- Whether an allowlist entry exists that admits it **without** admitting arbitrary exec. If the
  answer is "codex needs to spawn freely", the honest conclusion is that codex cannot be an
  isolated reviewer either — and that should be stated rather than engineered around.

## Next step

Instrument which exec or syscall is refused, before changing the profile. Widening
`(deny process-exec*)` by guesswork is the trap that has been refused twice today already —
first with grok, then with the credential-directory deny.
